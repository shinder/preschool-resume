# 公益開源評估

日期：2026-08-19
背景：評估「以公益角度將本專案開源」的利弊與前置工作。結論先講：支持開源——
商業路線在 `01_專案背景與定位.md` 已被查核到最低優先且未經買家驗證，開源
損失的獨佔價值很小，而公益價值（對抗官方下架、歸戶透明化）反而扎實。但
「程式碼開源」與「資料開放」是兩件事，應分開決策，且動手前有三件風險工作
必須先完成。

## 一、為什麼開源的代價很低

1. **程式碼不是護城河。** `03_資料源與護城河.md` 的判定：兩個全國集中源、
   一支爬蟲即可取得，資料取得門檻低，仿製門檻本來就低。開源爬蟲與網站程式
   碼幾乎不損失獨佔價值。
2. **真正的資產是歷史備份，且累積優勢多半不在我們手上。** 時間累積型的裁罰
   備份是唯一的結構性門檻，但 kiang 已備份多年；我們從 2026-08 才起步，
   獨佔這份資料的商業意義有限。
3. **守著的商業選項尚未驗證。** B 端路線（資料 API 賣給托育媒合平台）依
   `05_行動計畫.md` 應先訪談 2–3 家潛在買家，此事尚未發生。closed source
   保護的是一個未驗證的假設；開源換來的社群檢驗、信譽、與 g0v／kiang 生態
   互補則是確定的收益。`01` 第三節本就預想「與公益專案不搶流量、互相連結」，
   開源等於把這個關係做實。

## 二、程式碼開源與資料開放是兩件事

本題的公益缺口正是「官方公告到期即下架」。因此：

- **只開程式碼、不開資料，公益意義很薄。** 公益價值的主體是裁罰歷史備份
  資料集本身。
- **全開放**：定期釋出資料 dump（CC BY 4.0，標示政府資料開放授權來源），
  進入 g0v 生態，與 kiang 互補。公益價值最大。
- **中間路線（open core）**：資料 dump 延遲釋出（例如落後 30 天），即時
  異動偵測與推播 API 保留為未來的付費 SLA 服務。開源與 B2B 不互斥，資料
  型公益專案常見此模式。若仍想保留 B 端可能性，建議走這條。

## 三、開源前必須完成的三件事

1. **區分「官方事實」與「系統推論」。** 負責人歸戶、換牌重開偵測、觀察
   名單、警示分級都是推論結果，錯誤會指向真實的個人（名譽、個資法風險）。
   閉源時這是產品品質問題，開源公益化後是公信力問題。演算法公開受檢驗是
   好事，但呈現層必須明確標示推論性質，並提供申覆／更正管道。此點與
   `07_警示分級與負責人歸戶改善方向.md` 的個資紅線判斷一致：負責人歸戶
   的對外呈現仍應等法律意見，開源不改變這條紅線。
2. **清理 secrets——含整個 git 歷史。** wrangler 設定、old-mini 排程
   runner 的憑證、曾評估的 LINE token 等。用 `git filter-repo` 清歷史，
   或以乾淨歷史另建公開 repo（較省事，建議後者）。
3. **授權分層。** 程式碼用 MIT 或 Apache-2.0；自建的歸戶與備份資料集
   另以 CC BY 4.0 釋出，並依政府資料開放授權條款第 1 版標示原始來源
   （`03` 第五節）。

## 四、維運與可接手性

開源不會自動有人接手維運：爬蟲排程目前跑在 old-mini 上
（`08_old-mini_換機復原_runbook.md`），開源後它還是我們的機器。若要讓
專案「公益化到別人可以接手」，應把排程改成任何人 fork 即可復活的形式
（GitHub Actions 定時執行是首選）。這比 license 選擇更決定專案能否在
我們停止維護後存活。
